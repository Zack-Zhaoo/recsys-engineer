# 灵感孵化与实验进化

## 目标

灵感管理不是收藏链接，也不是把每篇论文变成待办。目标是让外部研究经过场景适配、成本判断和时间沉淀，转化为能增加系统认知的行动。

## 目录

- 第一步：忠实捕获
- 第二步：分流
- 第三步：冷却与聚类

- 第五步：把结果变成认知

- 状态机

## 第一步：忠实捕获

记录原始表达、触发来源、目标模块、核心机制、未知项和归属。新颖性默认 `unverified`。不要在记录时替用户补写不存在的效果或“首创”声明。

## 第二步：分流

使用两个主维度：

- **场景适配度**：是否对应当前系统的真实问题，数据与反馈是否匹配；
- **实现成本**：是否需要重构链路、大规模训练、新基础设施或长周期协作。

分流规则：

| 条件 | 去向 | 默认动作 |
|---|---|---|
| 高适配、低成本 | 孵化 TODO | 数天至一周后复看，准备最小实验 |
| 中等适配或中等成本 | 保持待判断 | 补齐场景差异与最小实现 |
| 低适配或高成本 | 长期灵感库 | 保存认知，不承诺立即实现 |

## 第三步：冷却与聚类

低成本想法也不要求立即编码。冷却数天至一周有两个价值：

1. 大脑继续处理问题，可能形成比论文原方案更适合当前系统的实现；
2. 相似 idea 可以聚合，统一设计特征、数据和消融，减少重复实验。

复看时记录 `local_adaptation` 和 `related_ideas`。不要为了按时清空 TODO 而跳过适配。

## 第四步：最小实验

实验不以复现完整论文为默认目标。优先验证最有启发、最贴近当前系统的机制：

- 明确当前工业 Baseline；
- 只改最关键的组件；
- 写出预期影响的人群、物料、漏斗输出和指标；
- 设计能快速推翻假设的检查；
- 限定时间、算力和工程预算；
- 预先定义继续、调整和停止条件。

## 第五步：把结果变成认知

指标不好很正常。复盘时区分：

- 原理不成立；
- 原理可能成立，但实现不充分；
- 总体无收益，特定人群或场景有信号；
- 模块输出改善，但下游没有消费；
- 收益被延迟、成本、生态或其他副作用抵消；
- 方案失败，却验证了重要系统边界。

每次实验必须写 `knowledge_gained`。如果没有形成新认知，也没有改变下一步动作，再漂亮的实验表格也价值有限。

## 第六步：快速迭代

上线或离线结果不理想时，先寻找可针对性优化的地方。下一轮应是最小、明确、能区分原因的改动，而不是一次叠加多项技巧。快速迭代不等于无限迭代。

## 第七步：停止与协同判断

出现以下信号时考虑停止：

- 核心假设已被直接反证；
- 连续多轮没有目标机制应出现的中间信号；
- 实现与维护成本超出潜在收益；
- 场景差异无法通过局部适配解决；
- 出现机会成本显著更低的新方向；
- 继续优化只能依赖无边界调参。

归档前做一次协同校准：同事可提供历史实验、技术细节和替代实现；负责人可判断业务优先级、资源与机会成本；产品和数据伙伴可解释用户行为。私人讨论不写入公开知识，个人工作区只记录必要结论和它如何改变决策。

## 状态机

```text
captured
  → incubating
  → clustered / developing
  → experiment-ready
  → experimenting
  → adopted / validated / rejected / archived
```

- `adopted`：已进入真实系统或稳定方案；
- `validated`：核心假设得到证据，但尚不等于已上线；
- `rejected`：当前假设被证据否定；
- `archived`：有保留价值，但当前不继续投入。

停止状态不删除原始表达、失败原因、咨询结论和认知产物。

## 复盘模板

```yaml
hypothesis: 为什么认为方案有效
expected_signal: 预期改变哪个中间量和业务切片
actual_result: 实际结果
diagnosis: 当前最可信的解释
next_iteration: 下一轮最小改动
knowledge_gained: 新增了什么系统认知
consultation: 与哪些角色校准了什么问题
decision: iterate | adopt | validate-only | reject | archive
```
