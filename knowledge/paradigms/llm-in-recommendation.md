# LLM 与推荐

LLM 在推荐中的角色应明确区分，否则“用了 LLM”没有技术含义。

## 四种角色

1. **表示与特征增强**：编码标题、评论、画像或多模态描述。
2. **数据/监督增强**：生成解释、属性、难负例、偏好摘要或教师标签。
3. **直接推荐器**：把推荐任务转成提示、问答、排序或生成任务。
4. **交互与编排层**：理解自然语言意图并调用检索、排序和外部工具；进一步见 [Agentic 推荐](agentic-recommendation.md)。

## 代表工作

- P5 将多个推荐任务统一为文本到文本范式，展示了 prompt-based recommendation 的通用接口。[SRC-P5-2022]
- TALLRec 用轻量调优让 LLM 适配推荐任务，代表“通用语言能力 + 推荐适配”的路线。[SRC-TALLREC-2023]

## 侵入性谱系

决定一个方案能否落地的，往往不是模型多先进，而是它要改动既有系统多少。把公开工作按侵入程度排开，会看到一条相当规整的对应关系。

| 位置 | 对既有系统的改动 | 已知落地状态 |
|---|---|---|
| 只贡献一个特征 | 排序模型与漏斗都不动，语义相似度作为一路特征接入 | 已上线，收益在千分之几量级 |
| 替换打分函数中的一项 | 保留链路，把即时目标换成长期价值估计 | 已上线，报告为统计显著 |
| 做控制面调参数 | 不替换任何模块，对既有参数做有界增量覆盖，主线兜底 | 已上线，收益在百分之几量级 |
| 替换排序模型本身 | 漏斗与上下游契约不动，换掉模型结构与训练方式 | 已上线，报告订单提升在百分之几量级 |
| 取代整条链路 | 重建召回、排序与列表组织 | 尚无工业落地，多在小候选集的原型中验证 |

同一家公司在相近时期发表的两项工作可以直接对照：一项把语义表征作为一路特征接入既有排序模型，订单提升在千分之几量级；另一项替换排序模型本身，订单提升到百分之几量级。改动越深，收益越大，验证与回滚的代价也越高。

侵入性、落地难度与收益幅度目前是同向的。想要大幅收益就得动大手术，而动大手术的方案还没有在真实系统中跑通；已经跑通的，无一例外都很克制。

因此选型时先确定能接受多大的侵入性，再挑对应量级的方案，而不是先看方法是否新颖。工业落地文章里最值得读的部分，通常也不是它用了什么模型，而是它如何把改动限制在可回滚的范围内、成本报到什么精度、以及哪些尝试失败了。

## 优势与边界

LLM 擅长冷启动语义、开放词表、自然语言约束、解释和跨域知识；但闭源模型版本漂移、成本、延迟、ID 协同信号不足、幻觉和不可重复性会阻碍核心高 QPS 排序。

文本化 ID 并不会自动学到协同过滤。若实验仅在候选很小、文本信息强的数据集上进行，不能直接推断其可替代工业检索和排序。

## 评估清单

- 与纯协同、纯内容、融合模型比较，并控制候选集和外部知识。
- 报告 seen/unseen item、冷启动、流行度分桶与跨域迁移。
- 统计 token、延迟、吞吐、缓存命中与调用成本。
- 检查事实性、可控性、隐私泄漏、提示注入和模型版本稳定性。
- 解释是否用到了测试期间不可得的信息。
