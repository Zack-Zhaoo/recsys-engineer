# Agentic 推荐

Agentic 推荐把推荐从一次打分扩展为有状态的决策过程：系统理解目标、维护记忆、规划步骤、调用检索/排序/搜索等工具、向用户澄清，并根据反馈修正策略。

## 最小定义

一个系统至少具备以下两项并形成闭环，才适合称为 Agentic：

- 持久或会话记忆；
- 多步规划与反思；
- 可选择、调用并校验工具；
- 主动提问或偏好获取；
- 对行动结果进行状态更新。

只有 LLM 生成推荐文案，或单次调用排序 API，不足以说明 Agentic。

## 2026-08 快照

- RecMind 较早把规划、工具使用和自我启发引入 LLM 推荐 Agent，并在公开任务上评估通用能力。[SRC-RECMIND-2024]
- RecGPT V1/V2/V3 连续探索生成式推荐 Agent、真实工业场景和更完整的 Agentic 系统；V3 在 2026-07 公开，代表该路线仍快速演化。[SRC-RECGPT-V1-2025] [SRC-RECGPT-V2-2025] [SRC-RECGPT-V3-2026]
- RecBot 类工作关注可交互、可澄清的推荐 Agent，体现推荐从被动 feed 向目标导向对话延伸。[SRC-RECBOT-2025]
- ClawRec 把推荐的运行位置移出平台，放进用户授权的个人 Agent 环境，跨来源维护任务态并组织互补列表。它的观察面是浏览器行为，消费面是本地渲染的 HTML 页面，评测建立在自建的模拟 benchmark 上，没有生产部署。作为范式探索有价值，同时也是场景假设不成立的典型样本，见下文两节。[SRC-CLAWREC-2026]

公开证据仍以论文原型和少数平台报告为主。Agentic 推荐尚未形成像双塔/精排那样稳定的工业标准栈。

## 参考架构

`用户请求 → 意图/约束解析 → 用户记忆 → 计划器 → 工具路由 → 检索/排序/知识工具 → 验证器 → 推荐与解释 → 反馈写回`

核心排序器通常仍存在。Agent 负责“何时问、查什么、调用哪个模型、如何组合结果”，而不是替代所有模型。

## 研究问题

- 记忆应保存事实、偏好还是决策轨迹；如何处理过期、冲突与用户删除。
- 如何衡量澄清问题的价值，避免为了互动而互动。
- 工具路由错误、级联幻觉和不可恢复动作如何被约束。
- 多 Agent 分工是否真的优于单 Agent + 明确工具，还是只增加 token 与误差传播。
- 即时满意、任务完成和长期偏好塑造如何共同评估。

## 评估框架

至少拆成：推荐质量、任务成功率、澄清轮数、工具成功率、记忆正确率、延迟/成本、安全违规、用户可控性。用固定回放集测确定性，再用模拟用户和真人实验补足交互性；模拟器分数不能替代真人效果。

## 约束穿透检查

工业推荐的全部工程学，是在四个约束下做近似：意图不可观测、候选空间巨大、反馈分布有偏、决策必须在毫秒内完成。Agentic 工作常常不是解决了这些约束，而是换到了一个不存在它们的场景——个人 Agent 环境里候选只有几十条，合成 benchmark 里任务是预设的，离线评测里没有旧策略造成的曝光偏差，研究原型不报延迟。

因此在评估收益之前，先逐条核对它绕开了几个：

| 约束 | 被绕开的典型迹象 |
|---|---|
| 意图不可观测 | 任务或意图由数据集预设、由 LLM 直接读到，而非从行为推断 |
| 候选空间巨大 | 候选只有几十条，每条都负担得起一次 LLM 判断 |
| 反馈分布有偏 | 数据为合成或公开小集，不含历史策略造成的曝光偏差 |
| 毫秒级延迟 | 不报 P99、token 成本与吞吐 |

绕开得越多，其结论越不能外推到工业系统。四个都绕开的工作实际在解另一个问题，即使它用 NDCG、Recall 等推荐指标叙述结果；此时"打败基线"往往只说明有结构的流程优于无结构的流程，与推荐本身无关。

ClawRec 是四条同时成立的样本。任务由模拟 benchmark 预设，候选被检索预算压到几十条，数据为合成故不含历史曝光偏差，全流程贪心调用 LLM 且未报延迟与成本。其最强基线是去掉编排组件的同一 Agent，因此报告的提升说明的是编排结构有效，而非推荐质量可比。[SRC-CLAWREC-2026]

这不否定其价值：问题定义、状态设计或列表组织方式仍可能值得迁移，但迁移的是思路，不是结论。反向用法同样成立——若某工作在四个约束齐全的条件下仍取得收益，其证据强度显著高于同类原型。

本节为综合判断，由多篇 Agentic 原型工作与工业系统常识归纳，不来自单一来源。

## 三个位置决定方法的自由度

约束穿透检查判断的是问题难度有没有被绕开，这一节判断的是场景本身成不成立。方法层的空间，多数时候由三个位置先定死。

**观察面**，系统从哪里看到用户行为。第三方 Agent 目前能稳定拿到的只有浏览器，读不到移动 App 内部。这不是实现偏好，是唯一开着的门。

**消费面**，用户在哪里看到推荐结果。独立页面、通知、系统级入口和 App 内嵌，能承载的条数、可打断程度和失败代价完全不同。

**时机**，什么时候出现。Feed 可以容忍低精度，因为划走的成本接近零；主动推送每错一次都要付信任的账，精度要求高一个量级。研究原型常见的规避办法是渲染成一个页面等用户自己来看，代价是失去主动性，也就退回成了一个需要用户想起来才会打开的工具。

三处定下来，方法层剩的空间就不大了。展示位从二十条压到一两条时，互补性筛选让位给打断决策，核心问题从"这些条目怎么搭配"变成"这一次该不该出现"。反过来，看到一份精心互补的二十条列表，通常说明作者手里有一个网页要填满。

ClawRec 的来源池取自知乎、小红书、淘宝、百度这类移动为主的产品，观察面却假设在浏览器，消费面是一个本地网页。这个矛盾被模拟轨迹抹平了：造出来的行为可以自由假设用户在浏览器里逛了某个 App，真实日志里这一步未必存在。[SRC-CLAWREC-2026]

## 行业规律

在移动为主的市场，跨 App 的观察位只属于操作系统与手机厂商，其次是超级 App 在自有生态内的局部视野。自托管的个人 Agent 拿不到这个位置。判断一个跨平台 Agentic 方案能否落地，先问它假设的观察面归谁所有，再问这个所有者有没有开放的动机。

这条判断也决定了平台侧的风险形态。真正可能把内容平台降级为候选供给方的，不是个人 Agent，而是预装在大量设备上的系统级助手。它不必解决候选规模问题，只做任务态识别与分发，把召回和排序留给各家 App 自己。相关立场见 [RS in AI](../../perspective/frontier-theses/rs-in-ai.md)。

## 实验设置的检查项

场景是否成立，多数时候能从实验设置里读出来。

- 数据是真实日志还是模拟轨迹。模拟轨迹会连同不成立的观察面一起造出来，场景不成立时，方法指标再高也不说明问题。
- 最强基线是不是同一系统去掉组件后的消融。若是，结论只能支撑"有结构优于无结构"，与推荐质量无关。
- 反馈回路有没有真的转起来。用留出行为当答案，是数据集在揭晓，不是用户看着推荐结果做出的反应；写进状态更新公式里的点击与跳过因此仍属假设。
- 观察面、消费面与出现时机有没有被显式声明。没有声明时，读者无法判断结论换一个界面还剩多少。

本节同样为综合判断。

作者重点关注 Agent 对用户画像的推理、行为与语义信号协同、小模型承接、推理效率和长期产品目标，而不是简单增加 Agent 步骤。详见 [Agentic Recommendation 主张](../../perspective/frontier-theses/agentic-recommendation.md)。
